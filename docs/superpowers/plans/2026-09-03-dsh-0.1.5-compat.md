# DSH 0.1.5 compatibility and v0.9.2-rc.2 release record

> Systematic debugging + TDD + verification-before-completion. Supersedes the
> first revision of this document, whose root cause was wrong.

## Reported symptom

`dsh-quota-panel@0.9.2-rc.1` on `@deepseek-ai/dsh@0.1.5-rc.1`:

```
Error: dsh: plugin tree failed to load: failed to apply loader entry quota-panel
(dsh-quota-panel): cannot get property "webServer" without inject
    at new apply (.../dsh-quota-panel/lib/index.js:1758:24)
```

## Root cause (verified, twice corrected)

`HostConnectionService.register()` (dsh-client-connection 0.1.5-rc.1:618) ends
with:

```js
return owner.effect(() => owner.webServer.register(route), `... rpc channel`);
```

`owner` is `this.ctx` read inside the tracked `rpc` getter. Cordis's traceable
service proxy invokes that accessor with a *shadow* receiver whose
`symbols.shadow` holds the **Connection plugin's own context**, so the later
`owner.webServer` read resolves the service on the Connection plugin's fiber
chain — never on the calling plugin's. That chain does not hold `webServer`, so
the read throws `cannot get property "webServer" without inject`.

Two consequences that the first fix attempt got wrong:

1. Declaring `webServer` in the plugin's static `inject` is **not** sufficient;
   the read does not consult the caller's store.
2. Wrapping the call in `ctx.inject(['webServer'], ...)` is **also** not
   sufficient. Measured on a real 0.1.5-rc.1 boot with a temporary probe inside
   the isolated profile copy:

   ```
   [probe] apply entered; inject= [ 'connection', 'credentials', 'webServer' ]
   [probe] inject callback; store= [ 'webServer' ]
   [probe] handle THREW: cannot get property "webServer" without inject
   [probe] handle returned undefined
   ```

   The throw happens inside a **child fiber**, so DSH boots cleanly and the
   channel silently never registers — worse than the original loud crash.

## Fix

Mount the endpoints through Connection's **exact Fetch registry**, which only
needs `owner.effect`: five in-box DSH plugins use it
(`dsh-client-ui-deliverables`, `dsh-client-file-upload`,
`dsh-api-session-controller`, `dsh-session-log-export`, …). The registry is
dispatched by Connection's own `/api` route, which applies the trusted-host +
browser-session fence before reaching plugin code.

- `RPC_CHANNEL = '/api'`, `RPC_METHOD_PREFIX = 'dsh-quota-panel'`,
  `RPC_ENDPOINTS` = specs, fetch-all, chatgpt-auth-status, chatgpt-login-start,
  chatgpt-login-cancel, chatgpt-logout.
- Host: one `connection.fetch.register({ path: rpcRoutePath(endpoint),
  methods: ['POST'], requestBody: 'buffered', fetch })` per endpoint, plus an
  envelope layer reproducing Connection's wire contract
  (`{type:'server-response', rpcId, result}`, `result` either
  `{ok:true,value}` or `{ok:false,error:{code,message,details}}`, `details`
  always an object).
- Browser: still Connection's client RPC helper, now
  `rpc.call('/api', 'dsh-quota-panel/' + endpoint, payload)`.
- Static `inject` returns to `['connection', 'credentials']` — `webServer` is no
  longer needed.
- Security: the endpoints move from an unauthenticated loopback path to DSH's
  own `/api` fence, so README security notes were updated accordingly.

## Evidence

- `npm run check` (build + 159 dual-face assertions) green.
- Real boot, DSH 0.1.5-rc.1, isolated `DSH_HOME` built from the packed tarball:
  boot clean, `POST /api/dsh-quota-panel/specs` → 200 with
  `{"type":"server-response","rpcId":"final-1","result":{"ok":true,"value":{"rows":[…]}}}`,
  advertised client module `/plugins/??dsh-quota-panel/client.js&rev=…` → 200
  (68 KB).
- The CI boot-gate script was extracted verbatim from `.github/workflows/ci.yml`
  and re-run locally against the packed tarball: **exit 0**; against the
  pre-fix `HEAD` build: **exit 1** with
  `RPC endpoint /api/dsh-quota-panel/specs unknown to the API channel (404)`.
- CI gate corrections (needed for any plugin to pass on 0.1.5): establish the
  browser session from the startup `?token=` URL, resolve the client bundle
  from the boot payload's advertised module URL, and probe the new `/api` path.

## Disposition of v0.9.2-rc.1

PR #9 is merged and its Volcengine dual-plan feature is kept; rc.1 stays
published on npm but must not be promoted: on current DSH its endpoints are
missing. rc.2 supersedes it on the same 0.9.2 line.

## Release

`package.json` is at `0.9.2-rc.2`. Publishing runs through the existing
`workflow_dispatch` release workflow (rc channel → npm `next` + GitHub
prerelease) after `check` and `boot` pass on `main`.
