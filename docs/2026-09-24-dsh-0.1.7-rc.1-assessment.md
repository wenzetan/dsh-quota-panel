# dsh-quota-panel × DSH 0.1.7-rc.1 适配评估

> 日期：2026-09-24 ｜ 目标宿主线：`@deepseek-ai/dsh@0.1.7-rc.1`（npm `next`）
> 基线宿主线：`0.1.5-rc.1` … `0.1.5-rc.3`（npm `latest`；实测可用 pin 为 `0.1.5-rc.3`，见 §4.5）
> 方法：`npm pack` 拉取 0.1.5-rc.1 与 0.1.7-rc.1 两版真实 tarball 逐包 diff（`.d.ts`
> 导出面 + 编译产物 + README），再用 testbed Docker 与真实 headless 浏览器在
> 0.1.7-rc.1 上实测装配、RPC 与浏览器半边。

## 0. 结论摘要

- 0.1.7-rc.1 对**本插件的运行时接缝**是兼容的：宿主侧 `connection.fetch.register` /
  `credentials.resolve`，浏览器侧 `slots` / `timer` / `connection` / `locale` 的
  签名与语义均未破坏；0.1.5 时代的 `connection.rpc.handle` 缺陷在 0.1.7 **依旧存在**，
  本仓库改用精确 Fetch 路由的决策仍然必要。
- 真正打到本仓库的有两处：
  1. **boot 图的客户端 bundle URL 变成 document-relative**（`/plugins/…` → `plugins/…`），
     直接使 testbed 的 L2 探针与 CI boot 任务的 client 探针失效（已实测复现）；
  2. **`@deepseek-ai/dsh-client-runtime` 已经不存在于 0.1.5/0.1.7 两线**
     （最后发布 0.1.1-rc.2），本仓库 `dsh.client.inject` 里那条是幽灵边，
     `slots` 服务的提供方早已换成 `@deepseek-ai/dsh-client-ui-renderer`。
- 0.1.7 **新增**了插件/宿主版本门禁（`evaluatePluginCompatibility`）：任何
  `@deepseek-ai/dsh*` peer 不满足当前宿主即拒绝启动/管理（该能力 0.1.7 才引入，
  更旧的宿主没有门禁）。既然**不再需要跨宿主线兼容**（旧宿主线用旧插件版本），
  本仓库现在主动把五个接缝包以精确版本 `0.1.7-rc.1` 声明为 peer：0.1.7+ 宿主按
  门禁放行/拒绝，旧宿主忽略声明；这同时满足 hub catalog 的收录资格（见 §6）。
- 改动后：`npm run check`、testbed L1、testbed 全部 node 测试（265 条）、
  0.1.7-rc.1 真实 testbed 全流程（含 L2 RPC + 真实浏览器执行客户端 bundle）全部通过。

这次实测证明了**探针改动本身**与宿主线无关。）

**（b）声明 peer 之后**：同一棵树在 `0.1.5-rc.3` 上**依然全绿**——因为版本门禁是
0.1.7 才有的能力，旧宿主根本不检查 peer，只是照旧加载。也就是说：精确 peer 在
0.1.7+ 宿主上 fail-loud，在更旧的宿主上被忽略（"不承诺支持"而非"技术上拒绝"）。
门禁本身的判定用容器内直接调用 `dsh-app-boot` 验证（§6.2）：

```
runtime: 0.1.7-rc.1
issue on current runtime: NONE (compatible)
issue when runtime is 0.1.5-rc.3: {"@deepseek-ai/dsh-client-connection":"0.1.7-rc.1", …}
```

**（c）`0.1.5-rc.1` 的上游安装布局问题**（与本仓库改动无关，已用 HEAD 纯净源码复现）：
该版本的全新全局安装本身就起不来：

```
Error: dsh: plugin tree failed to load: dsh: plugin(s) failed to load:
  @deepseek-ai/dsh-sandbox-local; Cordis startup failed because these plugin(s)
  could not be resolved
```

根因（已在镜像内定位）：`@deepseek-ai/dsh@0.1.5-rc.1` 对同族包用 `^0.1.5-rc.1`
范围，npm 会把它们解析到 **0.1.5-rc.3**，于是 `@deepseek-ai/dsh-base@0.1.5-rc.3`
（它依赖 `dsh-sandbox-local@^0.1.5-rc.3` 等）被装在
`…/dsh/node_modules/@deepseek-ai/dsh-base/node_modules/…` 深处，而
`dsh-base@0.1.5-rc.3` 的 patch 行以裸名 `@deepseek-ai/dsh-sandbox-local` 声明
该插件，加载器只在安装锚点/profile 解析 → 解析不到 → 拒绝启动。0.1.5-rc.3 整族
版本自洽，不受此影响；0.1.7-rc.1 更进一步，把 72 个同族依赖全部精确 pin
（无 `^`/`~`），因此全新安装天然自洽。

## 6. 本轮追加的三项决策与落地

### 6.1 CI 的 `not-in-hub`：根因与修复状态

`omdsh-dev/dsh-hub-workshop` 的 catalog 政策（`catalog.json#policy.dependencies`）原文：

> Native community plugins need a versioned production, peer, or optional
> `@deepseek-ai/dsh` dependency that is referenced by a runtime entry, patch, or
> plugin manifest. Wildcard/workspace/local specs and devDependencies never
> qualify a project by themselves.

本仓库此前只有 `@deepseek-ai/cordis` / `react` 两个 peer，**没有任何 `dsh-*` 依赖**，
因此被排除在 673 个已收录仓库之外（catalog `stats.pendingRepositories` 里）。现在
五个接缝包以精确版本进入 `peerDependencies`（其中四个在 `package.json#dsh.client.inject`
中被引用，满足 "referenced by … plugin manifest"），政策条件已满足；下一次 catalog
刷新应把本仓库收录。在刷新前：CI 的 plugin_check 因无 `gh` 认证而跳过 hub 检查
（保持绿），本地已登录 `gh` 的运行仍会报 `not-in-hub`。

补充（`INTAKE.md`）：新版提交要绑定 `package.json#dshWorkshop`
（`omdsh-workshop-package/v1`）；本仓库目前走的是"**遗留 `dsh.bundle` 制品兼容映射**"
路径（与已收录的社区 bundle 插件同类），可被收录，但 install/isolation/热重载等维度
在采用该 manifest 前保持 unknown。若要拿到"已审核/featured"级别，需要后续补
`dshWorkshop` manifest——属可选跟进项。

### 6.2 不再需要跨宿主线兼容

* `peerDependencies` 精确 `0.1.7-rc.1` + `peerDependenciesMeta.optional`：
  - 门禁实测（容器内直接调用 `dsh-app-boot` 的 `evaluatePluginCompatibility`）：
    ```
    runtime: 0.1.7-rc.1
    issue on current runtime: NONE (compatible)
    issue when runtime is 0.1.5-rc.3: {"@deepseek-ai/dsh-client-connection":"0.1.7-rc.1", …}
    ```
    即 **0.1.7+ 宿主**会按此拒绝加载；0.1.5 线宿主没有门禁（该能力 0.1.7 才引入），
    会忽略 peer 声明照旧加载——实测 `DSH_VERSION=0.1.5-rc.3` 的 testbed 全流程仍通过。
    政策语义是"不承诺支持旧线"，而不是"在旧线上主动报错"。
  - optional 让 profile 安装不引入额外包（实测 profile `node_modules` 仍只有
    `dsh-quota-panel`），也避免 npm 用户端自动安装五个 dsh 包。
* 旧宿主线的用户保留旧插件版本；README 已写明"一次只支持一条宿主线"。

### 6.3 版本与 tag 约定（已落地）

约定：`package.json#version` = `<dsh线>-v<本地号>`（例：`0.1.7-rc.1-v0.1`，合法 semver），
git tag = `v` + 该版本号（`v0.1.7-rc.1-v0.1`）。DSH 线不新增字段——
`peerDependencies` 的精确版本是唯一事实来源。

`ci.yml` 已按此重写：

1. `on.push.tags` 改为 `v*`；`workflow_dispatch` 输入改为 `release`（布尔）——
   在维护线分支上创建并推送该分支 `package.json#version` 对应的 tag，再派发发布运行
   （`release-tag` job）。
2. `tag` job（main 推送自动打 tag）改为 `v$(package.json version)`，不再区分
   "rc / stable"——通道由下一步决定。
3. 新增 `classify` job：校验 tag 与 `package.json#version` 一致，读取
   `npm view @deepseek-ai/dsh dist-tags`，把**宿主线自己挂的 dist-tag** 作为发布通道
   （`latest` → npm `latest`；`next`/`alpha` → 对应 tag；无匹配 → 回退 `next`）。
4. `release-pre`（通道 ≠ latest）：GitHub pre-release + `npm publish --tag <通道>`，无需审批。
5. `release-latest`（通道 = latest）：GitHub 正式 release + `npm publish --tag latest`，
   保留 `production` 环境的人工审批。
6. 删除 `promote` job：新模型下"转正"就是 dsh 自己把该线上调到 `latest`，插件随
   dist-tag 自动跟随，不再需要手工孪生 tag。
7. `boot` job 不再硬编码 dsh 版本：从 checkout 的 `@deepseek-ai/dsh*` peer 解析宿主线，
   使维护线的发布在自己那条宿主线上过门禁。

实测（本地复现 workflow 里的解析逻辑）：

```
peer 解析: 0.1.7-rc.1        tag: v0.1.7-rc.1-v0.1
通道解析: 0.1.7-rc.1 → next   0.1.5-rc.3 → latest   未知线 → next
```

发布记录：`v0.1.7-rc.1-v0.1` → npm `next`；`v0.1.5-rc.3-v0.1`（维护分支
`release/0.1.5-rc.3`）→ npm `latest`。历史 npm 版本由维护者统一 deprecate；
GitHub 上旧格式的 release/tag 一并清理。
