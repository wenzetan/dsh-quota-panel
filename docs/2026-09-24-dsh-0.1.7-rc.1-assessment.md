# dsh-quota-panel × DSH 0.1.7-rc.1 适配评估

> 日期：2026-09-24 ｜ 目标宿主线：`@deepseek-ai/dsh@0.1.7-rc.1`（npm `next`）
> 基线宿主线：`0.1.5-rc.1` … `0.1.5-rc.3`（npm `latest`；实测可用 pin 为 `0.1.5-rc.3`，见 §4.5）
> 方法：`npm pack` 拉取 0.1.5-rc.1 与 0.1.7-rc.1 两版真实 tarball 逐包 diff（`.d.ts`
> 导出面 + 编译产物 + README），再用 testbed Docker 与真实 headless 浏览器在
> 0.1.7-rc.1 上实测装配、RPC 与浏览器半边。

## 0. 结论摘要

- 0.1.7-rc.1 对**本插件的运行时接缝**是兼容的：宿主侧 `connection.fetch.register` /
  `credentials.resolve`，浏览器侧 `slots` / `timer` / `connection` / `locale` 的
  签名与语义均未破坏；0.1.5 时代的 `connection.rpc.handle` 缺陷在 0.1.7 **依旧存在**，
  本仓库改用精确 Fetch 路由的决策仍然必要。
- 真正打到本仓库的有两处：
  1. **boot 图的客户端 bundle URL 变成 document-relative**（`/plugins/…` → `plugins/…`），
     直接使 testbed 的 L2 探针与 CI boot 任务的 client 探针失效（已实测复现）；
  2. **`@deepseek-ai/dsh-client-runtime` 已经不存在于 0.1.5/0.1.7 两线**
     （最后发布 0.1.1-rc.2），本仓库 `dsh.client.inject` 里那条是幽灵边，
     `slots` 服务的提供方早已换成 `@deepseek-ai/dsh-client-ui-renderer`。
- 0.1.7 **新增**了插件/宿主版本门禁（`evaluatePluginCompatibility`）：任何
  `@deepseek-ai/dsh*` peer 不满足当前宿主即拒绝启动/管理。本仓库不声明 dsh peer，
  故不受影响；这也意味着**不应**为了"统一版本"而新增精确 peer——那会让插件在
  0.1.5 线上被门禁拒之门外。
- 改动后：`npm run check`、testbed L1、testbed 全部 node 测试（265 条）、
  0.1.7-rc.1 真实 testbed 全流程（含 L2 RPC + 真实浏览器执行客户端 bundle）全部通过。

### 4.5 旧线（0.1.5-rc）现状实测与一个上游安装布局问题

用同一棵改动后的源码在旧线上复核（`DSH_VERSION=0.1.5-rc.3`，`STEPS=all`）：

```

[testbed][0.1.5-rc.3][local][l2] specs rows=3 refreshMs=60000

```

（旧线 boot 图仍广告绝对路径 `/plugins/…`，适配后的探针归一化是恒等变换 → 无回归。）

同一棵树固定到 **`0.1.5-rc.1`** 时，真实 boot 在加载任何插件之前就失败（已用 HEAD
纯净源码复现同样的失败，与本仓库改动无关）：

```
Error: dsh: plugin tree failed to load: dsh: plugin(s) failed to load:
  @deepseek-ai/dsh-sandbox-local; Cordis startup failed because these plugin(s)
  could not be resolved
```

根因（已在镜像内定位）：`@deepseek-ai/dsh@0.1.5-rc.1` 对同族包用 `^0.1.5-rc.1`
范围，npm 会把它们解析到 **0.1.5-rc.3**，于是 `@deepseek-ai/dsh-base@0.1.5-rc.3`
（它依赖 `dsh-sandbox-local@^0.1.5-rc.3` 等）被装在
`…/dsh/node_modules/@deepseek-ai/dsh-base/node_modules/…` 深处，而
`dsh-base@0.1.5-rc.3` 的 patch 行以裸名 `@deepseek-ai/dsh-sandbox-local` 声明
该插件，加载器只在安装锚点/profile 解析 → 解析不到 → 拒绝启动。0.1.5-rc.3 整族
版本自洽，不受此影响；0.1.7-rc.1 更进一步，把 72 个同族依赖全部精确 pin
（无 `^`/`~`），因此全新安装天然自洽。

结论：旧线应固定 **0.1.5-rc.3**（而非 `0.1.5-rc.1`），这也是本次把版本声明统一到
单一自洽版本的理由之一。

## 5. 存疑 / 需人工决策
1. **`plugin-check` 的 `not-in-hub` warning**：与本升级无关，但 `scripts/plugin-check.mjs`
   对 warning 零容忍，会在 hub catalog 可达时把 CI 门禁打红。需人工决定：在 hub
   workshop catalog 登记本仓库，或把该 warning 明确列为豁免项。
2. **是否声明 `@deepseek-ai/dsh*` peer**：0.1.7 引入的门禁让 peer 声明具有强制语义。
   声明精确版本（如 `0.1.7-rc.1`）能拿到门禁保护，但会拒绝 0.1.5 线；本仓库当前刻意
   不声明（`.d.ts`/服务面已验证兼容）。若要收紧，建议用范围（如 `^0.1.0`）并跑两线 testbed。
